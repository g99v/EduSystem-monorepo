# Grafana gateway and JWT issuer monitoring

The actual Kong Compose file and `gateway/kong-docker-compose.yaml` include
Prometheus and Grafana. The configuration lives in this folder and uses
`EDUSYSTEM_BACKEND_DIR`, so the template works on Windows and Arch Linux without
copying monitoring files into the separate Kong repository.

## Open the dashboard

- Grafana: http://localhost:3000/d/edusystem-gateway
- Initial learning login: `admin` / `admin`, unless overridden using
  `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` beside your actual Compose file.
- Prometheus targets: http://localhost:9090/targets

Grafana provisions the Prometheus data source and **EduSystem Gateway & JWT
Issuer** dashboard automatically. There is no manual dashboard import. Grafana
may prompt you to change its initial password; the changed password persists in
its named volume. Environment credentials only initialize a new Grafana database.

The dashboard shows:

- Gateway and issuer scrape health, Kong database reachability, request counts,
  server errors, traffic by route/status and p95 request/upstream latency.
- Login-route response counts separately from actual issuer executions and
  outcome categories such as `issued`, `credentials`, `csrf`, `verify_timeout`
  and `signing`.
- Average and p95 HTTPS credential-verification and JWT-signing durations,
  handler latency and concurrent issuer executions.
- Nginx connections, Kong worker Lua VM memory, Node process memory/CPU and
  event-loop lag. Lua VM memory does not represent total Kong container memory.

Use the time-range picker and gateway route selector. Route selection only
affects gateway panels; issuer panels always show the dedicated login plugin.

Prometheus scrapes every 10 seconds. Rates need several samples, and request
latency/signing panels need actual requests. Empty timing charts immediately
after startup are expected; sign in through your normal frontend to populate
them. No sample credentials or simulated login requests are generated by this
setup. Count panels use Prometheus `increase`, so values are sampled estimates
over the selected range rather than an audit ledger.

## Start or update on either machine

From your actual Kong Compose directory:

```sh
docker compose build kong
docker compose up -d --no-deps --wait kong prometheus grafana
```

Your Windows directory is
`C:/Users/Moham/Desktop/Kong/docker-kong/compose`. On Arch, copy the shared
Compose template to your existing Kong Compose location and set
`EDUSYSTEM_BACKEND_DIR` to the local absolute `tutorial` directory.

The gateway already has its global Prometheus plugin enabled. Monitoring does
not require a gateway database sync or an application migration. For a fresh
gateway database, follow the normal `kong-config` setup documented in
`../../docs/MTLS.md`.

Pinned runtime images are Grafana 13.2.3 and Prometheus 3.15.0, including their
published image digests. The JavaScript exporter uses the maintained
`@prometheus-io/client` 0.16.1, pinned in the package lockfile.

## Metrics and logging

Prometheus reads the Kong Status API at `kong:8100/metrics`, and the JavaScript
plugin server at `kong:9464/metrics`. These ports are not published on the host.
Grafana and Prometheus UI ports bind to host loopback. The three services share
the Compose monitoring network; the existing gateway and database networks
remain in use.

The plugin server exports these application metrics:

| Metric | Meaning |
| --- | --- |
| `edusystem_jwt_issuer_requests_total{outcome}` | Completed access-handler executions, categorized using a fixed vocabulary. |
| `edusystem_jwt_issuer_in_flight` | Current access-handler executions. |
| `edusystem_jwt_issuer_duration_seconds` | Histogram of handler duration before PDK logging/response exit. |
| `edusystem_jwt_issuer_stage_duration_seconds{stage="verify"\|"sign"}` | Histograms of attempted verification/signing, including failed attempts. |

Default Node process metrics share the `edusystem_jwt_issuer_` prefix. Metrics
never contain emails, account IDs, credentials, tokens or correlation IDs.
Metadata discovery creates neither a metrics listener nor default process
collectors; the normal plugin server starts the internal exporter after loading
its key/TLS material.

Preflight, size-limit and rate-limit responses can complete before the issuer
runs. Their gateway counts therefore differ from plugin execution counts.
The plugin's direct HTTPS call also bypasses Kong's normal upstream proxy timing;
use the credential-verification panels for that call.

Detailed per-execution logs are available separately:

```sh
docker compose logs -f --tail 100 kong
```

`KONG_LOG_LEVEL=info` enables the plugin's existing correlation ID, outcome,
verification duration and signing duration logs. This setup provides metrics in
Grafana; it does not install a log-storage service.

Prometheus retains up to 15 days or 2 GB of samples in `prometheus_data`, and
Grafana stores its settings in `grafana_data`. Restarting or recreating containers
preserves both named volumes. Plugin/gateway counters reset when their processes
restart; Prometheus rates account for these resets. A plugin-server restart can
lose events between the last scrape and shutdown.

## Checks performed

JavaScript syntax, plugin metadata discovery, Compose parsing and dashboard JSON
are checked during setup. Service startup, scrape targets and provisioned
dashboard availability are checked against the running containers. No tests are
written or run, and existing test files and Liquibase changelogs remain untouched.
